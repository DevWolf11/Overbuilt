# Tests

The game has no build step and no test framework, so these are plain Node scripts. The headless ones load the game's own `js/` files into a Node VM (see `lib/game.js`), with no DOM or WebGL, and drive the real physics, combat, ground combat and multiplayer code. The browser ones open the game in headless Chromium through Playwright. There are 29 headless suites and 22 browser ones (the lists are at the top of `run.mjs`), plus seven tools that `run.mjs` doesn't run (below).

```
node test/run.mjs              # the headless suites, side by side, about 3½ minutes
node test/run.mjs --browser    # plus the browser suites, one at a time, about an hour
node test/run.mjs traces mp    # only suites whose file names contain these words (browser ones too:
                               #   "mp" also runs browser/mp-two-tabs.mjs; "mp.test" is the headless one)
node test/run.mjs -v           # print every suite's output, not only failures
node test/run.mjs traces --update   # rewrite the named suites' baselines (no name: all of them)
node test/traces.js            # any single suite runs on its own too
```

You need Node 18 or newer, plus Playwright and a Chromium: the browser suites need them, and so does the one-off decoding of the Earth map that the headless suites use (see below). If `PLAYWRIGHT=/path/to/playwright/index.mjs` is set, that is used; otherwise a local install, then the global one (`npm root -g`). Set `CHROMIUM=/path/to/chrome` to use a particular browser. The 3D view runs on software WebGL (SwiftShader), so no GPU is needed.

## Tools

Seven scripts that `run.mjs` leaves out: three for when you change the drawn ground (the arena's, the near ground) or the ground physics, one to prove which baseline keys a change moved, one to measure what a change to the 3D view costs, and two that measure the drones' balance:

```
node test/tools/arena-probe.js           # Highland Ridge on the real map, about 90 s
node test/tools/ground-probe.js          # the ground drawn round a craft against the physics', eleven places, about a minute
node test/bench/ground-bench.mjs         # ground physics timings; name words narrow it ('rounds', 'collisions', 'MA-1'), --secs 5
node test/tools/keydiff.mjs 68ea3fe      # every baseline key against a ref; --allow file:key[=f1|f2],... --add file:key,...
node test/bench/render-bench.mjs --base ../ob-base --check   # the 3D view before and after (the water's: --scenes coast,slipway,lake,sea,sea300,sea3k), 30-45 minutes on 4 cores (--scenes, --profiles, --quality narrow it)
node test/tools/drone-strike.js 80     # what kamikaze drones do to tanks (bumble tk34 ...: only those), ROOT=<checkout> for another
node test/tools/drone-strike.js 30 --spots tk72 ma1   # ...by spot; --kill: hits to kill at good and poor spots; --ai / --lock: the computer's or a lock-on drone
node test/tools/cuas-run.js 60         # how often counter-drone kit stops a drone flying in (gun laser2 ...: only those)
node test/tools/cuas-run.js 40 gun --ap=level,look,acro   # ...flown in as a player flies (straight level look acro weave side high lock auto); ai:gun ai:jam ...: the computer's drone
```

- **`tools/arena-probe.js`** measures Highland Ridge, the Ground Battle arena in North Scotland: each pad's and zone's height, steepest slope and water; every line of sight between pads and zones over the curved Earth, and the share of ground each sees from 300 to 1,200 m; each berm's slope and dryness, and that no berm opens a line of sight from a pad to the other pad or to a zone; the Scotland airfield's clearance. Then the drawn ground against the physics' ground: the terrain patch round each pad and zone (its RMS out to 600 m, with every airfield's strip and blend left alone by the arena's detail fade), and the arena's own ground mesh within 0.1 m RMS and 0.3 m of the physics everywhere in the arena, on high and low. Run it after anything that changes the arena's heights (a berm, a pad, the fade) or its props: what the player sees must be what the shells hit. Since the props update its lines of sight count the props that block sight (`PROPS=0` leaves them out) and it checks the design's pairs: the hilltop sees the slope and the village, no pad sees the other or a zone.
- **`tools/ground-probe.js`** measures the ground drawn against the physics' ground outside Highland Ridge, at eleven places (the runway's apron, the tank yard, the spawn outposts of the Faroes, Shetland and Scotland, a Shetland hill, the slope test path and lowland Scotland), 1,200 points each within 100 and 300 m of a craft on the ground: the terrain patch as its triangles draw it (`test/lib/patch.js`, render3d's `patchJob` rebuilt in Node, shared with arena-probe), centred on the craft and 300 m off as when it is about to be rebuilt, and the near ground (`Render3D.nearGeo`, its window of tiles on the physics' own lattice, each tile's cells chosen and stitched as the page does) on high and low, read as its triangles draw it. Every node worked out must be the physics' own height to the bit (float32), the ground drawn within 5 cm everywhere within 64 m of the craft on high (32 m on low) and within 1 m further in (past it the cells are 8-32 m; the rim, which blends into the patch in the page, is reported alone), with no jump across any tile's or block's edge (a crack: 2 mm at most, about 0.3 mm found); each window's tiles are listed by their finest cells. Run it after anything that changes how terrain.js works out a height or its lattice, or the near ground's tiles.
- **`tools/drone-strike.js`** flies stock drones (Bumble FPV and Fibre, Lancett, a Bumble with a frag or a tandem charge) into stock tanks (TK-34, MA-1, MA-1C, BMK-2D) along the attacks a player flies, from seeds: dives of 45-80° at 20-35 m/s onto the turret roof (35%) and the engine deck (25%), 25-50° onto the turret's back (15%), and shallow hits on the rear (15%) and the side (10%), the aim jittered ±0.5 m. Each run is destroyed (an ammunition detonation), knocked out, half (an engine, track, gun or gunner out, a crewman dead, a fire, a blow-out) or nothing, and for nothing it says what the fuse met and what the round did. `tools/cuas-run.js` flies a hostile Bumble straight at a parked tank from 1.5 km at 30 m/s, 30-60 m up, from a random bearing, diving on its turret from 70 m out, and counts how often the tank's kit stops it (gun, gun and detector, laser, two drones 3 s apart, the MA-1C with radio and fibre drones). The second balance pass gave both more: drone-strike.js aims at each spot (`--spots`: good ones, the roofs, the turret's back and ring and the side above the tracks; poor ones, the glacis, the turret's face and a reactive brick), counts hits to kill with drones one after another 4 s apart (`--kill`), and flies the computer's drones (`--ai`) or a player's on lock-on (`--lock`); cuas-run.js flies the ways a player comes in (`--ap=`: straight, `level` slowing to 15 m/s 250 m out, `look` stopping 3 s to look, `acro` at 45 m/s low, `weave`, `side` past 70-110 m abeam then in, `high` diving from 120-150 m, `lock` a scripted path with the lock-on's flag set, `auto` the real lock-on flying itself: its fate is the game's lock, through, down, or jammed when a jammer made it let go before its dive), a hand-flown drone at an enemy kit tank, counts a quad that lost a motor or its radio as down unless it falls on the tank and leaves out runs that hit a hill, and `ai:<kit>` sends the Tank Range's attack Bumble from a random bearing. drones.test.js §13 runs a few of each.
- **`tools/keydiff.mjs`** compares every `baseline/*.json` in the working tree with the same file at a git ref (a commit, branch or tag), key by key and field by field, and fails (exit 1) on any key that moved, appeared or went missing unless it was allowed: `--allow fingerprint:falcon=mass|com` lets those fields of that key move (`file:key` alone any field, `file:*` any key of the file), `--add traces:bumble` lets a key be new; a key or a whole file gone is never allowed. It checks the checkout it sits in, wherever it is run from (`--repo dir` for another). Run it after `--update`, to show that only the keys a change was meant to move moved (the method of PRs #36 and #38); its header has the details.
- **`bench/ground-bench.mjs`** times the ground vehicles headless: microseconds per physics step and terrain calls per step (counted through the `Terrain` object, as vessel.js and gear.js make them), stepped as `driving.js` steps them; then collisions (`Gear.bump`) and the cost of an autocannon round and a main-gun shell over their lives. Timings depend on the machine, so compare runs made on one machine.
- **`bench/render-bench.mjs`** measures the 3D view's cost and picture in headless Chromium, where SwiftShader does the GPU's work on the CPU, so a finished frame's wall time stands for the GPU's: twelve fixed scenes (the runway, low over land, the sea facing the Sun, the most built-up town, 10 km up, Highland Ridge's village, a battle there full of effects, a dogfight, an anti-drone gun's fight (airbursts 10 a second round two drones, tracers, a laser's beam; judged as the battle is), dusk, the hangar, and `combo`, the whole update's busiest picture: eight knocked-out tanks in Highland Ridge's street, the three nearest burning and smoking at the game's own rates, two drones under the anti-drone gun's airbursts and a burning plane overhead, judged only by its GPU ratio, at most 1.25), the drone's camera views when named (`--scenes fpv,fpvfast,fpvchase`), the water's when named (`--scenes coast,slipway,lake,sea300,sea3k`: a Buggy on the space centre island's west coast and on the headland's slipway, a Falcon 120 m over a loch and 300 m and 3 km over the open sea; each checks there is water within 300 m), and two more only when named (`--scenes rangefight,wrecks8`: a Hostile range fight with two bandits shot down and one crashing, and eight knocked-out tanks burning, smoking and baked in Highland Ridge's street, both with the simulation stepped in every timed frame, so their `cpuMs` is a whole frame's JS; reported against the base, never judged by `--check`, since each tree plays its own rules) on a phone in portrait (390×844, DPR 2, a 4× CPU slowdown for the CPU's share) and a desktop (1280×720), High and Low, the pixel ratio pinned. Per scene: the median frame time (`gpuMs`; the base and current trees take turns, a round of frames each, and B/A is the median of the rounds' own ratios, so the machine's changing load hits both alike), the CPU's share (`cpuMs`: the same frames with `Render3D.skipDraw`), draws and vertices by pass (canvas, shadow map, env cube) counted from the WebGL calls, `Render3D.info()`, programs created, particle fill in screens, and the pixels (FNV-1a hash, the share that differ, PNGs with `--shots`); `--cpuprofile` adds a CPU profile of the battle. `--base <dir>` names the tree to compare against, a worktree of the commit before (`git worktree add ../ob-base 68ea3fe`): it serves both, patches each copy of `render3d.js` at two frozen anchors (`const perf = { ema: 1 / 60, scale: 1, at: 0 };` and `function adaptResolution(dt) {`, so leave them as they are) to pin the pixel ratio, read the render clock and what is still being built, so a tree without the `Render3D.bench` hooks is measured exactly as one with them, and both draw the very same frames (Math.random reseeded before each): a change that should not touch the picture shows identical pixels (`--same` fails otherwise; a flight scene may differ in at most 0.01% of its pixels, a few far ones where surfaces tie in depth and go to whichever was made last, which 68ea3fe against itself shows now and then; the hangar in none). `--check` fails on a breach of the graphics spec's budgets (`gpuMs` ratios per kind of scene, the CPU's share, draws, vertices, programs, textures, fill, the hangar's pixels). The scenes' times of day and places are constants in the file, found with `--find-times`, and each scene checks it is what it stands for (noon light, dusk's warmth, water under the sea scene, the town's buildings, the village's props, no glass in the hangar's craft). A full run (48 scene runs, twelve scenes on two profiles at two qualities) takes about 55 minutes on a 4-core machine (3-8 minutes a scene; run a scene at a time with `--scenes` to keep each result as it comes) (31 and 42 at the big update's first phase, the second with `--cpuprofile`); `--save out.json` keeps the numbers.

## Baselines

A baseline is the output of the code on `main`. The suites that have one compare against it and print each difference. When a change is **meant** to alter results (new physics, a new part in a template, retuned handling), check that the differences are the ones you expect and nothing else. Then rewrite the baseline:

```
node test/traces.js --update        # one suite
node test/run.mjs traces --update   # the same through the runner; with no suite named, every baseline
```

Commit the new baseline with the change, and say in the commit why it moved; `node test/tools/keydiff.mjs main --allow …` (under Tools) proves key by key that nothing else did. A refactor that should change nothing must leave every baseline identical. That is the main point of `traces.js`: it shows even a last-digit change in any template's flight.

## How it works

- **`lib/game.js`** runs `util.js`, `space.js`, `terrain.js`, `parts.js`, `vessel.js`, `gear.js`, `aim.js`, `armour.js` and the big update's `drone.js` (plus `combat.js`, with `radar.js` and `death.js` after it, `world.js`/`flight.js` or `mp.js` on request, and `gmode.js` and `groundai.js` with any of them or with `ground: true`) in one VM context, the way the page does. The ground update's and the big update's files load only if they are there, so `ROOT` can still point at a checkout from before them; `G.load({ drone: false })` leaves `drone.js` out, so a suite can prove old play is the same without it. It stubs `Sound`, `FX` and `Settings` where needed. `combat.js` gets its internals exposed as `Combat._t`.
  - `G.craft()` builds a vessel the way `Flight.start` does (parts, joints, the part tree holding the control part, stages), then places it on its kind's launch site, or 3 km over the sea with `'air'`. Unlike `Flight.start`, it doesn't move float planes to the bay or idle a helicopter's throttle.
  - `G.sim()` is a stand-in for `Flight`.
  - `G.load({ props: true })` builds every map's props at load. The old baselines' suites (`traces.js`, `fingerprint.js`, `handling.js`, `driving.js`, `combat.test.js`) load with it, so their baselines staying identical proves the props change nothing where none stands (old shots and craft never build a map themselves).
  - `G.run(ctx, code)` runs code inside the game's scope. Top-level `const`/`class` names aren't properties of the context; use `G.run` to reach them, or add them to the list at the end of `load()`.
  - `ROOT=/other/checkout node test/...` runs a suite against another copy of the game. That is handy for comparing against an older commit (`git worktree add /tmp/old <commit>`).
- **`lib/earth.js`** provides the real Earth map. Node can't decode the PNG and JPEG layers, so the first run decodes them once in Chromium (`lib/dump-earth.mjs`, exactly as the game does) into `test/.cache/earth/` (gitignored, about 28 MB). The cache is redone automatically when the size of any file in `assets/` changes; after a re-bake that keeps the sizes, run `node test/lib/dump-earth.mjs` by hand. So even the headless suites need Playwright, once.
- **`lib/browser.mjs`** provides a static server on a free port, the Chromium launch flags, a fresh game profile (`openGame`) and the same ok/FAIL check list. Screenshots land in `test/.cache/shots/`. Headless Chromium with software WebGL runs the sim at about 0.08× real time, so a browser test must wait on `Flight.time`, never the wall clock, and can set `Render3D.skipDraw = true` where the picture doesn't matter.
- **`lib/baseline.js`** compares results with a baseline or rewrites it.
- **`lib/tanks.js`** gives the stock ground vehicles as design rows, read from the checkout's own `builder.js` exactly as the builder loads them: `tk34`, `ms4`, `tygr`, `ma1` and `pumo` by name, and every ground template, the Desert Technical too, by its key in `all`. `G.craft(ctx, T.tk34, 'tank')` builds one.
- **`lib/mptrace.js`** records a scripted multiplayer session step by step (a 2v2 air battle through every phase, a second one that runs out of time, then a sandbox with every kind). It uses only what `mp.js` had before the ground update, so the same script runs against an older checkout; `mp.test.js` compares it with `baseline/mp-air.json`.

## Writing a new check

Put it in the suite it belongs to, or copy a small one such as `core.test.js`. Prefer checks that would fail on a real regression: compare with numbers worked out independently (a brute-force sum, a mirror image, a round trip), not with the code's own output. For whole-game behaviour, extend a fingerprint. Run the suite before and after your change to the game: it should pass before and fail without your fix.
