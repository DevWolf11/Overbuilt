# Tests

The game has no build step and no test framework, so these are plain Node scripts. The headless ones load the game's own `js/` files into a Node VM (see `lib/game.js`), with no DOM or WebGL, and drive the real physics, combat, ground combat and multiplayer code. The browser ones open the game in headless Chromium through Playwright. There are 20 headless suites and 11 browser ones (the lists are at the top of `run.mjs`), plus two tools that `run.mjs` doesn't run (below).

```
node test/run.mjs              # the headless suites, side by side, about a minute
node test/run.mjs --browser    # plus the browser suites, one at a time, about a quarter of an hour
node test/run.mjs traces mp    # only suites whose file names contain these words (browser ones too:
                               #   "mp" also runs browser/mp-two-tabs.mjs; "mp.test" is the headless one)
node test/run.mjs -v           # print every suite's output, not only failures
node test/run.mjs traces --update   # rewrite the named suites' baselines (no name: all of them)
node test/traces.js            # any single suite runs on its own too
```

You need Node 18 or newer, plus Playwright and a Chromium: the browser suites need them, and so does the one-off decoding of the Earth map that the headless suites use (see below). If `PLAYWRIGHT=/path/to/playwright/index.mjs` is set, that is used; otherwise a local install, then the global one (`npm root -g`). Set `CHROMIUM=/path/to/chrome` to use a particular browser. The 3D view runs on software WebGL (SwiftShader), so no GPU is needed.

## Tools

Two scripts that `run.mjs` leaves out, for when you change the arena's ground or the ground physics:

```
node test/tools/arena-probe.js           # Highland Ridge on the real map, about 90 s
node test/bench/ground-bench.mjs         # ground physics timings; name words narrow it ('rounds', 'collisions', 'MA-1'), --secs 5
```

- **`tools/arena-probe.js`** measures Highland Ridge, the Ground Battle arena in North Scotland: each pad's and zone's height, steepest slope and water; every line of sight between pads and zones over the curved Earth, and the share of ground each sees from 300 to 1,200 m; each berm's slope and dryness, and that no berm opens a line of sight from a pad to the other pad or to a zone; the Scotland airfield's clearance. Then the drawn ground against the physics' ground: the terrain patch round each pad and zone (its RMS out to 600 m, with every airfield's strip and blend left alone by the arena's detail fade), and the arena's own ground mesh within 0.1 m RMS and 0.3 m of the physics everywhere in the arena, on high and low. Run it after anything that changes the arena's heights (a berm, a pad, the fade) or its props: what the player sees must be what the shells hit. Since the props update its lines of sight count the props that block sight (`PROPS=0` leaves them out) and it checks the design's pairs: the hilltop sees the slope and the village, no pad sees the other or a zone.
- **`bench/ground-bench.mjs`** times the ground vehicles headless: microseconds per physics step and terrain calls per step (counted through the `Terrain` object, as vessel.js and gear.js make them), stepped as `driving.js` steps them; then collisions (`Gear.bump`) and the cost of an autocannon round and a main-gun shell over their lives. Timings depend on the machine, so compare runs made on one machine.

## Baselines

A baseline is the output of the code on `main`. The suites that have one compare against it and print each difference. When a change is **meant** to alter results (new physics, a new part in a template, retuned handling), check that the differences are the ones you expect and nothing else. Then rewrite the baseline:

```
node test/traces.js --update        # one suite
node test/run.mjs traces --update   # the same through the runner; with no suite named, every baseline
```

Commit the new baseline with the change, and say in the commit why it moved. A refactor that should change nothing must leave every baseline identical. That is the main point of `traces.js`: it shows even a last-digit change in any template's flight.

## How it works

- **`lib/game.js`** runs `util.js`, `space.js`, `terrain.js`, `parts.js`, `vessel.js`, `gear.js`, `aim.js` and `armour.js` (plus `combat.js`, `world.js`/`flight.js` or `mp.js` on request, and `gmode.js` and `groundai.js` with any of them or with `ground: true`) in one VM context, the way the page does. The ground update's files load only if they are there, so `ROOT` can still point at a checkout from before it. It stubs `Sound`, `FX` and `Settings` where needed. `combat.js` gets its internals exposed as `Combat._t`.
  - `G.craft()` builds a vessel the way `Flight.start` does (parts, joints, the part tree holding the control part, stages), then places it on its kind's launch site, or 3 km over the sea with `'air'`. Unlike `Flight.start`, it doesn't move float planes to the bay or idle a helicopter's throttle.
  - `G.sim()` is a stand-in for `Flight`.
  - `G.load({ props: true })` builds every map's props at load. The old baselines' suites (`traces.js`, `fingerprint.js`, `handling.js`, `driving.js`, `combat.test.js`) load with it, so their baselines staying identical proves the props change nothing where none stands (old shots and craft never build a map themselves).
  - `G.run(ctx, code)` runs code inside the game's scope. Top-level `const`/`class` names aren't properties of the context; use `G.run` to reach them, or add them to the list at the end of `load()`.
  - `ROOT=/other/checkout node test/...` runs a suite against another copy of the game. That is handy for comparing against an older commit (`git worktree add /tmp/old <commit>`).
- **`lib/earth.js`** provides the real Earth map. Node can't decode the PNG and JPEG layers, so the first run decodes them once in Chromium (`lib/dump-earth.mjs`, exactly as the game does) into `test/.cache/earth/` (gitignored, about 28 MB). The cache is redone automatically when the size of any file in `assets/` changes; after a re-bake that keeps the sizes, run `node test/lib/dump-earth.mjs` by hand. So even the headless suites need Playwright, once.
- **`lib/browser.mjs`** provides a static server on a free port, the Chromium launch flags, a fresh game profile (`openGame`) and the same ok/FAIL check list. Screenshots land in `test/.cache/shots/`. Headless Chromium with software WebGL runs the sim at about 0.08× real time, so a browser test must wait on `Flight.time`, never the wall clock, and can set `Render3D.skipDraw = true` where the picture doesn't matter.
- **`lib/baseline.js`** compares results with a baseline or rewrites it.
- **`lib/tanks.js`** gives the stock ground vehicles as design rows, read from the checkout's own `builder.js` exactly as the builder loads them: `tk34`, `ms4`, `tygr`, `ma1` and `pumo` by name, and every ground template, the Desert Technical too, by its key in `all`. `G.craft(ctx, T.tk34, 'tank')` builds one.
- **`lib/mptrace.js`** records a scripted multiplayer session step by step (a 2v2 air battle through every phase, a second one that runs out of time, then a sandbox with every kind). It uses only what `mp.js` had before the ground update, so the same script runs against an older checkout; `mp.test.js` compares it with `baseline/mp-air.json`.

## Writing a new check

Put it in the suite it belongs to, or copy a small one such as `core.test.js`. Prefer checks that would fail on a real regression: compare with numbers worked out independently (a brute-force sum, a mirror image, a round trip), not with the code's own output. For whole-game behaviour, extend a fingerprint. Run the suite before and after your change to the game: it should pass before and fail without your fix.
