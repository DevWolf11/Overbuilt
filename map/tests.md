# Tests, docs and performance practice (test/, docs/HANDBOOK.md, README.md, CLAUDE.md, sw.js)

The tests are plain Node scripts with no framework. test/run.mjs runs 12 headless suites side by side (44 s on this box, with handling.js taking 40 s of that). With --browser it also runs 6 Playwright suites one at a time (4 min 08 s). Both sets pass on main at cc0e666.

The headless suites go through test/lib/game.js. It runs util, space, terrain, parts and vessel in a vm context, and on request combat (internals on Combat._t), world+flight, or mp with stubbed Net/UI/Flight/Builder. It pulls TEMPLATES, templateRows and RAIDER out of builder.js and combat.js with regexes.

Five suites compare against JSON baselines through lib/baseline.js: fingerprint, traces, handling, combat and mp-measure. Any changed, missing or new key counts as a difference. The others are ok/FAIL check lists.

Car coverage is thin:
- Only one template is a car (buggy). fingerprint, traces and mp-measure include it, as they do the dragonfly heli (car wheels plus chassis) and the rover.
- combat.json and handling.json are planes only.
- I perturbed the drive friction, the non-plane steering and the coast-down one at a time in scratch copies. Only traces.buggy moved each time.
- Changing the plane wheels' rolling friction moved nothing in any of the 12 suites. The ground roll of planes has no baseline at all.
- The buggy trace only reverses for 2 s and then coasts. No browser test drives a car or runs a battle.

Docs follow a fixed routine for each update:
- README: the What's in it bullets, the part, paint, template and mission counts in the prose, and the Controls table.
- The controls appear in three places: README, App.showHelp and Flight.controlsHelp.
- Handbook: the subsystem chapters, §6 Testing "New in PR #N" and §7 loose ends.
- CLAUDE.md: the architecture-table counts and a history row.
- sw.js: a CACHE bump (and SHELL entries for new files); net.js: a NET_VERSION bump with its reason added to the comment.

For PR #35, performance was measured with an ad hoc harness that is not in the repo but is still in the scratchpad. It counted WebGL and 2D-canvas calls, timed renderer.render, used CDP metrics and /proc CPU, and timed µs per physics step. Results were reported as before/after tables, with the baselines left byte-identical.

## Constraints
- Every existing baseline entry must stay byte-identical unless the change is meant to move it. New templates appear as 'new (not in the baseline)' entries in fingerprint, traces and mp-measure (and combat/handling if their kind filters match). Re-baseline with --update, and check in the diff that existing entries are unchanged ('additions only', as PR #36 did). Say why in the commit
- Shared ground code (vessel.js ground(), DRIVE.other, wheel friction and steering) also drives the buggy, the dragonfly (a heli with driven carWheels: aircraft = wings.length>0 is false for helis), the Lunar Rover and every plane's gear. traces.buggy is the only alarm for car changes, and plane ground roll has none, so add coverage before refactoring
- Don't change existing parts' keys, w/h, twinZ or z-lock (carWheel, chassis, chassisL, cab, wheel). Even a mass change moves fingerprint, traces and mp-measure for buggy and dragonfly. Add new parts instead
- Keep the regex and anchor contracts test/lib/game.js relies on: `const TEMPLATES = {` … `\n};`, `function templateRows(t) {` … `\n}`, `const RAIDER = [ … ]];`, and combat.js's final `  return {\n    S, step,`
- Headless suites run with no DOM: logic that tests need (ground physics, turret aim, ballistics, mode rules) must not touch the DOM, Settings or Sound at load time
- Physics must stay frame-rate independent at PHYS_DT 1/120. The 60 fps cap only skips frames. No per-frame allocation on flight or hangar paths. The idle hangar makes no GL call. A paused flight or one under a dialog draws 10/s and home draws 30/s (redraw.mjs enforces this)
- Phone layouts: portrait 390×844 and 375×667, landscape 844×390, desktop 1280×720. 'More…' must stay in sight in the tab strip for every kind. HUD additions must not overlap .telemetry, .left-controls or #mp-bar (rwr-hud pattern)
- Controls must match in README's table, App.showHelp and Flight.controlsHelp, plus the per-kind hints in flight.js and main.js:281
- sw.js: bump CACHE on any cached-file change. New js files go in SHELL, an index.html <script> in dependency order and a README Project layout line. Every SHELL entry must exist
- NET_VERSION must go up for new parts, new spawn/pv/snapshot fields, or owner-side behaviour that decides hits (ground turrets firing while landed)
- Player-visible names for real vehicles must be altered (as with Sugoi/MyG/FS); code comments may use real names
- The headless run is about 44 s now; new suites run in parallel, but keep each under about 20 s so the total stays near the documented 40-47 s. The browser run is 4 min
- Handbook citations are file:line and drift; fix them in the same commit when the code moves

## Risks
- Coverage gap: changing the rolling friction of non-driven wheels (plane gear, 0.025, vessel.js:994) passed all 12 headless suites unchanged. A ground-physics refactor could silently change plane taxi and takeoff (us4's takeoff check only tests thresholds)
- The only car trace (buggy) reverses for 2 s and coasts. Forward speed, cornering at speed, braking, slopes, water and flips are untested, so track or skid-steer work could break the Dune Buggy unnoticed
- rwr.test.js:138-141 defaults any military:true template to needing an Advanced RWR, so new military ground templates fail it unless the test or the templates are adjusted
- rwr.test.js:108-134 asserts that turrets never fire when touching the ground. A naive 'let turrets fire on the ground' change breaks it, and changes behaviour for the bomber turret and old car-mounted turrets (README:68 promises cars can't shoot with them)
- builder-shapes hard-codes tab counts (15, 7, 8). Any new category or tab order change fails the browser suite
- combat.test.js and handling.js filter on kind==='plane'. A new 'tank' kind slips past both, so ground combat has no fingerprint unless one is added
- mp.test's battleDesign check uses TEMPLATES[bd.name.toLowerCase()]: a ground fallback with a name that differs from its key throws inside the test
- No test exercises a PvP battle (phases, spawns, checkWin, results). A new game mode starts with zero automated coverage and needs both a headless state-machine test and a two-tab browser run
- G.craft throws for a kind without a VEHICLE_KINDS entry or with a site missing from EARTH.sites. Fingerprint, traces and mp-measure iterate every template, so one ground template with a new kind and no site breaks three suites at once
- Adding parts changes shapes.test's random pair sampling (fixed seed, new pool). Any new non-box part must pass builder-shapes' 1.5 cm model-vs-clash check, or needs CLASH_PAD/CLASH_BOXED
- The perf harness is not in the repo. The scratchpad copies point at a deleted worktree path and need repointing; numbers from SwiftShader on a shared 4-core box are only relative (the harness notes say counts are robust, wall and GPU ms are not)
- Many ground vehicles each stepping wheel or track contacts cost CPU: a driving buggy is about 37 µs/step in the browser (4.4 ms/s at 120 Hz) and the active craft never sleeps. Tracks with many contact points or AI tanks could multiply this; measure per-vehicle µs/step
- Agent worktrees under /home/user/Overbuilt/.claude/worktrees are excluded only through .git/info/exclude, not .gitignore. A `git add -A` from another clone setup could pick them up, and Pages publishes the whole checkout
